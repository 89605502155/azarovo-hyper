# Ресурсы хоста: RAM, CPU и диск без гонок

Прежде чем что-то создать или увеличить, библиотека проверяет, что хост это
может дать, и **забирает** ресурс тем же атомарным шагом. Если не может —
бросается `InsufficientResourcesError`, и после него ничего не остаётся: ни
образа диска, ни определения домена, ни занятого соединения.

```python
from azarovo_hyper import InsufficientResourcesError, hyper

try:
    vm = hyper().kvm(memory="64G", disk_size="2T", vcpus=128).start()
except InsufficientResourcesError as error:
    print(error)  # not enough host resources: memory: requested ...
    for s in error.shortfalls:  # Shortfall(resource, requested, available)
        print(s.resource, s.requested, s.available)
    print(error.resources)  # {'memory', 'disk', 'cpu'}
```

## Что проверяется

| Операция | RAM | vCPU | Диск |
|---|---|---|---|
| `start()` | потолок гостя (`memory` + добавленные DIMM) | `vcpus` (в сумме и на машину) | `disk_size` нового образа |
| `memory.plug()` | добавляемый объём | | |
| `cpu.set()` | | прирост; не больше CPU хоста | |
| `storage.attach(size=...)` | | | новый образ |

* **Запас RAM** = доступная память хоста − `host_memory_reserve` − то, что
  работающие гости ещё могут занять (их потолок минус уже занятое). Гость
  учитывается по потолку, потому что балун может в любой момент дорастить его
  до этого значения; поэтому `memory.set()` и не требует проверки.
* **Запас CPU** = CPU хоста × `cpu_overcommit` − vCPU работающих гостей.
  Одна машина никогда не получит больше vCPU, чем есть у хоста.
* **Запас диска** = свободное место на целевой файловой системе − `host_disk_reserve`.

## Почему гонки нет

Наивная схема «проверили, потом создали» ломается, когда двое проверяют
одновременно и оба видят одну и ту же свободную память. Здесь замер хоста,
проверка запроса и сам вызов гипервизора, который забирает ресурс (`create`,
хотплаг vCPU или DIMM, предвыделение диска), выполняются под одним
эксклюзивным замком на весь хост (`flock`), поэтому это работает между
**потоками и процессами**. Когда замок отпускается, гипервизор уже показывает
ресурс занятым, и следующий вызов это видит: ничего не учитывается дважды и
нет резервов, которые надо снимать. Замок охватывает только этот один вызов —
загрузка гостя идёт уже без него, — поэтому машины по-прежнему стартуют
параллельно.

Последний рубеж против программ, которые этот замок не берут, — ядро:

* диски создаются с `disk_preallocation="falloc"`, и место выделяет файловая
  система прямо при создании; нехватка места обнаруживается сразу;
* `memory_prealloc=True` заставляет QEMU выделить всю память гостя при старте;
* такие поздние отказы QEMU или `qemu-img` превращаются в тот же
  `InsufficientResourcesError`, а машина, которую `start()` только что
  определил, откатывается.

## Политика

```python
from azarovo_hyper import ResourcePolicy, hyper

vm = hyper().kvm(memory_overcommit=1.5, cpu_overcommit=8, host_memory_reserve="2G")
h = hyper(resources=ResourcePolicy(cpu_overcommit=2))  # по умолчанию для всех машин
lab = h.kvm(check_resources=False)  # отключить для одной машины
```

| Параметр | По умолчанию | Смысл |
|---|---|---|
| `check_resources` | `True` | выключить проверки |
| `memory_overcommit` | `1.0` | 1.0 никогда не обещает больше RAM, чем есть |
| `cpu_overcommit` | `4.0` | работающих vCPU на один CPU хоста |
| `host_memory_reserve` | `"512M"` | RAM, которая всегда остаётся хосту |
| `host_disk_reserve` | `"1G"` | место на диске, которое всегда остаётся свободным |
| `disk_preallocation` | `"falloc"` | `off` (тонкий qcow2), `metadata`, `falloc`, `full` |
| `memory_prealloc` | `False` | выделить всю память гостя при старте (KVM) |

Файл замка лежит в `$XDG_RUNTIME_DIR/azarovo-hyper/` (поменять — `AZAROVO_LOCK`).
Он согласует программы на одной клиентской машине; гостей, запущенных другими
инструментами, библиотека всё равно видит через цифры самого гипервизора.
